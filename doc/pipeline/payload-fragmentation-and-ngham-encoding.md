# Payload memory reading + NGHam packet encoding pipeline

## Objective

This task integrates the protocol understanding developed while studying NGHam with the FreeRTOS concepts covered in the reference lessons. It implements a 3-task FreeRTOS pipeline in C simulating the onboard flow for handling occultation event data (mock data standing in for actual payload memory reads): fragmenting it into chunks, passing it through a queue manager, and encoding each chunk into a complete NGHam frame — matching the sequence required on the actual MSP430 prior to transmission.

This runs on the FreeRTOS POSIX simulator rather than on MSP430 hardware. The objective at this stage is to validate the task/queue/encoding logic fully before addressing hardware registers and the CCS toolchain.

## Build system

The Makefile compiles each `.c` file into its own `.o` object file (`main.c`, the FreeRTOS kernel sources — `tasks.c`/`queue.c`/`list.c`/`timers.c`/`event_groups.c` — the heap manager, and the POSIX port files), then links all object files into the final binary. `-D_POSIX_C_SOURCE=200809L` is required because the FreeRTOS POSIX port depends on POSIX-specific functions (certain pthread and timing calls) not exposed by default under strict C standards, and `-lpthread` is required at link time since the POSIX port simulates each FreeRTOS task as an actual pthread.

## payload_chunk.h — shared data structure

```c
typedef struct {
    uint16_t occultation_id;
    uint8_t  sequence_number;
    uint32_t timestamp;
    uint8_t  total_chunks;
    uint8_t  data_size;
    uint8_t  data[CHUNK_DATA_SIZE];
} PayloadChunk_t;
```

This struct is the unit of data that flows through both queues in the pipeline:

- `occultation_id` — identifies which event a given chunk belongs to, since one event may be split across multiple chunks.
- `sequence_number` and `total_chunks` — allow the receiving side (eventually the ground station) to identify, for example, chunk 3 of 5, and reassemble data in the correct order.
- `timestamp` — generation time for the chunk, using `xTaskGetTickCount()`.
- `data_size` — number of valid bytes in `data[]`, since the final chunk of an event is typically smaller than `CHUNK_DATA_SIZE`.
- `data[CHUNK_DATA_SIZE]` — the payload bytes, fixed at 32 bytes per chunk. This chunk size was agreed upon with a collaborating teammate to ensure module interoperability.

Fixed-size chunks are used rather than variable-length ones because FreeRTOS queues require a known item size at creation (`xQueueCreate(10, sizeof(PayloadChunk_t))`) — queues copy fixed-size blocks and cannot hold a variable number of bytes per item. Fragmenting into a known maximum size is therefore the direct solution.

## main.c — task implementation

### Task 1: payload reader / fragmenter

Simulates reading payload memory for a set of mock occultation events:

```c
static const MockEvent_t mock_events[] = {
    { .occultation_id = 1, .data_size = 100 },
    { .occultation_id = 2, .data_size = 45  },
    { .occultation_id = 3, .data_size = 70  },
};
```

These stand in for actual payload memory reads (which would eventually come from flash or SRAM on the satellite). A buffer is filled with predictable synthetic bytes to allow visual confirmation that chunk-splitting behaves correctly in the printed output.

The number of chunks required per event is calculated using ceiling division:

```c
uint8_t total_chunks = (data_len + CHUNK_DATA_SIZE - 1) / CHUNK_DATA_SIZE;
```

Adding `CHUNK_DATA_SIZE - 1` before dividing ensures any remainder rounds up rather than down — e.g. 100 bytes over a chunk size of 32 requires 4 chunks, not 3, or the final 4 bytes would be lost.

Fragmenting and sending one chunk at a time (rather than an entire event in a single queue call) aligns with how the downstream tasks — and eventually the radio — process data: one chunk at a time. NGHam frames are themselves chunked messages, so this structure matches how the actual downlink would operate: one NGHam frame per queue item.

### Task 2: queue manager

```c
if (xQueueReceive(xQueue1_RawChunks, &chunk, pdMS_TO_TICKS(3000)) == pdTRUE)
{
    total_forwarded++;
    xQueueSend(xQueue2_OrderedChunks, &chunk, portMAX_DELAY);
}
```

This task is intentionally minimal — it receives from Queue 1 and forwards into Queue 2. It is implemented as a separate task, rather than having Task 1 write directly to Queue 2, specifically to allow future extension — reordering logic or priority-based scheduling between occultation events could be added here without modifying Task 1 or Task 3.

The idle branch — triggered if nothing arrives within 3 seconds — treats this as Task 1 having finished producing data, logs a final count, and places the task into an idle loop. This provides a simple mechanism for detecting pipeline completion without a separate signaling structure.

### Task 3: NGHam encoder

Converts the payload chunk into a complete, transmission-shaped packet.

**Step 1 — Serialize the chunk into a flat byte buffer:**

```c
ngham_payload[p++] = (uint8_t)(chunk.occultation_id >> 8);
ngham_payload[p++] = (uint8_t)(chunk.occultation_id & 0xFF);
ngham_payload[p++] = chunk.sequence_number;
memcpy(&ngham_payload[p], chunk.data, chunk.data_size);
```

NGHam has no knowledge of `PayloadChunk_t`; it operates on a flat byte array. Each metadata field is packed manually in big-endian order (most significant byte first), followed by the chunk data. Multi-byte fields are split manually with bit shifts rather than via a raw struct `memcpy`, since struct padding and endianness are not guaranteed to match across compilers or architectures — manual serialization avoids this class of bug.

**Step 2 — Build the NGHam packet:**

```c
int packet_len = ngham_build_packet(ngham_payload, (uint8_t)p, ngham_packet);
```

This calls into `ngham.h`, which performs the protocol-level work: selecting a size class, computing the header, CRC, padding, and Reed-Solomon parity, and assembling the complete frame with preamble and sync word.

**Step 3 — Log the frame** broken into its protocol fields (preamble, sync word, size tag, header byte, payload, CRC, padding, and RS parity), printed as separate labeled hex blocks rather than a single hex dump — this makes byte-offset errors immediately visible during development.

## main() — system wiring

```c
xQueue1_RawChunks     = xQueueCreate(10, sizeof(PayloadChunk_t));
xQueue2_OrderedChunks = xQueueCreate(10, sizeof(PayloadChunk_t));

xTaskCreate(vTask1_PayloadMemReader, "Task1", configMINIMAL_STACK_SIZE * 2, NULL, 1, NULL);
xTaskCreate(vTask2_QueueManager,     "Task2", configMINIMAL_STACK_SIZE * 2, NULL, 1, NULL);
xTaskCreate(vTask3_NGHamEncoder,     "Task3", configMINIMAL_STACK_SIZE * 4, NULL, 1, NULL);

vTaskStartScheduler();
```

Both queues hold up to 10 `PayloadChunk_t` items. All three tasks are assigned equal priority (1), since none requires precedence over the others — each waits on its queue and processes data as it arrives. Task 3 is allocated double the stack of the other two to accommodate its local buffers (`ngham_payload[64]` and `ngham_packet[300]`), which exceed the stack requirements of Tasks 1 and 2.

`vTaskStartScheduler()` transfers control to FreeRTOS permanently; the code following it does not execute under normal operation and exists only as a fallback if the scheduler fails to start (e.g. insufficient heap for the idle task).

## Hook functions

- `vAssertCalled` — backs `configASSERT`. If an internal FreeRTOS sanity check fails, this identifies the triggering file and line rather than failing silently.
- `vApplicationMallocFailedHook` — fires if FreeRTOS's heap is exhausted while allocating a task's stack or a queue's storage.
- `vApplicationStackOverflowHook` — fires if a task exceeds its allocated stack, identifying the specific task name.

These are required, not optional: `FreeRTOSConfig.h` enables `configCHECK_FOR_STACK_OVERFLOW` and `configUSE_MALLOC_FAILED_HOOK`, so the kernel expects these functions to be defined, or the build fails to link.

## ngham.h — NGHam protocol implementation

A from-scratch C implementation of the components of NGHam required to construct a valid frame, developed from the TTC 2.0 documentation and observed pyngham behavior.

### CRC16-CCITT

Standard bit-by-bit CRC16-CCITT: initializes to `0xFFFF`, XORs each byte into the top of the register, shifts left 8 times per byte (XOR-ing with polynomial `0x1021` when the top bit is set), and XORs the final result with `0xFFFF`. This matches the CRC scheme specified for NGHam frames and protects the header+payload portion of the packet against corruption, separately from Reed-Solomon, which protects the entire coded block.

### Size table

NGHam does not use a single fixed frame size; it selects from 7 predefined size classes, each with its own 3-byte size tag, RS(n,k) parameters, and maximum payload capacity. Smaller payloads use a smaller frame (less overhead, proportionally less RS protection); larger payloads use bigger frames with proportionally more parity bytes. `ngham_build_packet` selects the smallest size class that fits the payload, minimizing overhead.

### Reed-Solomon over GF(256)

This is the most technically involved part of the implementation, and a limitation is worth stating explicitly: the field polynomial used here (`0x11D`) is a common textbook/demo GF(256) polynomial, not the exact one specified in the official NGHam spec (`0x187`, with a specific generator root). The encoder is structurally correct — it implements a genuine, working Reed-Solomon systematic encoder — but will not necessarily produce byte-identical output to the official reference implementation unless the field polynomial and generator root are matched exactly. This is the next item to address before this needs to interoperate with a real ground station decoder.

With that noted, the implementation proceeds as follows:

- `gf_init()` builds log/antilog tables for GF(256) arithmetic, allowing multiplication in the field via `gf_exp[gf_log[a] + gf_log[b]]` rather than direct polynomial multiplication and modular reduction.
- `rs_generator_poly()` constructs the RS generator polynomial for the required number of parity symbols, using the standard iterative construction.
- `rs_encode()` performs systematic RS encoding via a polynomial-division-style shift register; the register's final contents form the parity. "Systematic" means the original data bytes appear unchanged in the output, with parity bytes appended afterward.

### ngham_build_packet() — frame assembly

1. Select a size class — the smallest one where `payload_len <= max_payload`.
2. Compute padding — `k - 3 - payload_len`, since the RS data block size `k` must be filled exactly: 1 header byte + payload + 2 CRC bytes + padding = `k`.
3. Build the header byte — currently holds only the padding size, masked to 5 bits per the NGHam header format.
4. Compute CRC over header+payload only; padding is filler and excluded from the integrity check.
5. Append zero padding until the data block reaches exactly `k` bytes.
6. Run Reed-Solomon on the full `k`-byte data block to produce `n - k` parity bytes.
7. Assemble the final frame: 4-byte preamble (`0xAA` repeated, aiding radio clock/data recovery lock), 4-byte sync word (`0x5D 0xE6 0x2A 0x7E`, marking frame start), 3-byte size tag, followed by the full data block and RS parity.

Returns `-1` if the payload exceeds the largest available size class; Task 3 checks for this and logs an error rather than constructing an invalid frame.
